# 🟢 pgrep -f 模式自匹配导致等待循环永不退出

==待处理== · 执行环境 · <kbd>S3</kbd>

---

> [!question]+ 结论
> `pgrep -f <pattern>` 匹配的是**完整命令行**，而等待循环自身的 argv 里就包含该 pattern，
> 于是循环条件**永远为真**，等待器永不退出 —— 表现为「后台等待任务永不完成」。

---

> [!quote] 发生了什么

**事实链：**

```
# 意图：等 runner 结束后自动跑校验
nohup bash -c 'while pgrep -f phase2r6a_mimo_formal >/dev/null 2>&1; do sleep 20; done;
               python3 .../phase2r6a_dual_validation.py' > AUTOVALIDATE.log 2>&1 &

# 实测匹配到的进程（pattern 自匹配）：
pgrep -f phase2r6a_mimo_formal
  60174  Python .../phase2r6a_mimo_formal.py     ← 真正的 runner
  64308  bash -c cd /Users/... &&                ← 外层包装（argv 含该字符串）
  64310  bash -c while pgrep -f phase2r6a_mimo_formal ... ← 等待器自身！

⇒ 即使 runner 60174 结束，64310 仍匹配自己 → 死循环
```

---

| 判断 | 依据 |
|:-----|:-----|
| ==是设计缺陷不是偶发== | `pgrep -f` 语义即为「匹配整条命令行」，等待器 argv 天然含该模式 |
| ==短模式尤其危险== | 用脚本名片段（如 `phase2r6a_mimo_formal`）必然自匹配 |
| ==用长模式也不稳== | 只要 pattern 出现在自身 argv 里就会自匹配，与长度无关 |

---

> [!warning] 可能偏差
> - 若 pattern 只出现在**子进程**argv 而不在等待器 argv（例如 pattern 由变量拼接且 shell 不展开为 argv），则不自匹配。
> - `pgrep -f` 在部分平台对自身 PID 有隐式排除，但**不保证**，实测 macOS 未排除。

---

> [!note]- 过程层（复盘时展开）
> **原话**：为等 10 次串行 MiMo 调用结束后自动跑双验证，写了 `while pgrep -f phase2r6a_mimo_formal; do sleep 20; done`。
>
> **关键分歧**：一度以为「后台任务已完成（exit 0）但日志为空」是 Python stdout 缓冲所致；
> 实际是 `pgrep` 自匹配使循环条件恒真。
>
> **标尺**：「等待条件的判据不能出现在等待者自己的命令行里」。
