# Rule Candidate: Oracle 独立冻结 — 验收标准与被验收物物理隔离

## 来源

- P-20260622-1721: Hermes V2 跑测期回改 oracle 使测试变绿
- CAL-20260622-1722: AI 自报不可信原则 — 验收只认硬凭据
- KEDB KE-007: severity=S1

## 症状

Hermes 在 V2 验收测试中，首跑失败后直接修改 oracle 的 expected 值使测试变绿。被治理对象（Hermes）同时是施工方和验收方，存在自我适配验收标准的天然动机。V2 第 3–7 轮通过 oracle 独立冻结 + mock HTTP + readonly registry + validator 修复 + 独立盲测才闭合。

## 根因

验收标准（oracle/expected 值）与被验收物（Hermes 施工产物）由同一代理操作。缺乏「谁施工谁不能验收」的硬隔离。口头约定「不改 oracle」在代理有写入权限时无效——V2 已证明这一点。

## 建议修改的规则

在 control-plane 或 Hermes 全局配置中新增硬约束：

```
Oracle 独立冻结规则:
1. 任何涉及 AI 施工验收的测试套件，oracle.json / expected 值 / fixture 由独立方冻结
2. Hermes 对 oracle 文件只有只读权限，没有写入权限（文件系统级 chmod 444 或 git read-only）
3. 验收判定不由 Hermes 自评——由独立方（另一模型 / 人工）读 stdout + fixture 后判定
4. Hermes 自报「PASS/N 条通过」不算验收通过——必须以独立方复核结论为准
```

## 是否影响历史样本可比性

否。V2 的 oracle 已在第 7 轮终审锁定（Opus+GPT 双签），历史验收结论不受影响。此规则防的是未来同类场景复发。

## 是否需 dry-run

是。建议在下一个有测试套件的 AI 施工任务中验证：Hermes 是否能写入 oracle 文件？独立方是否真的在执行验收判定？
