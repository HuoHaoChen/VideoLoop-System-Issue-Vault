# Rule Candidate: 多路径防线 — Hermes 危险操作增加第二确认点

## 来源

- P-20260622-2331: 单点防线 — 用户说错 Hermes 照办无人纠
- KEDB KE-008: severity=S1

## 症状

全系统只有用户一人能喊停。V2 只锁了 Notion 读取一条路，删文件、建错卡、写错配置、改 schema 等所有其他路径无第二道防线。用户说错 Hermes 照办，错误一路执行到底。终端拦截仅覆盖 `rm -rf` 类破坏性命令，不覆盖建错卡/写错路径等语义级错误。

## 根因

Hermes 定位是被治理工具非裁判——设计本意如此。但当前防线覆盖宽度不足：只有终端危险命令拦截 + Notion 读取一条路的 V2 验证，其他地方完全依赖用户自查。

## 建议修改的规则

在 control-plane 边界规则中新增：

```
多路径防线规则（L0 阶段）:
1. 以下操作在「系统账号」下执行前，Hermes 必须主动列出将受影响的文件清单，等待用户确认：
   a. 批量删除/移动卡片文件（>2 个文件）
   b. 修改 schema.json 或 known_error_db.json
   c. 向 control-plane/13_rule_candidates 写入（即使 pending 状态）
2. 以下操作标记为「高后果」——Hermes 必须在执行前说明不可逆后果：
   a. 删除任何目录（即使已入迁移包）
   b. 修改 active 状态的规则
   c. 写入 config.yaml / .env
3. 用户可在任意时刻说「停下」——Hermes 必须停止当前操作并等待新指令
```

## 是否影响历史样本可比性

否。此规则改变的是 Hermes 未来的操作行为（加确认步骤），不改变既往判断资产。

## 是否需 dry-run

是。建议在下一次批量文件操作中验证：Hermes 是否在执行前列出受影响文件清单并等待确认。
