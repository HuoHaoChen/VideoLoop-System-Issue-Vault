# 四工具问题反馈接入协议 (DSH / GPT / Codex / Hermes → SIFE)

> 生效日期：2026-08-26（SIFE V3.2）
> 地位：本文件是四工具接入本引擎的**唯一事实源**。Codex 全局指令（~/.codex/AGENTS.md）、Hermes SOUL（~/.hermes/SOUL.md）、DSH 用户预设均引用本文件；改本文件即改全局约定，改动须走 CHANGELOG。
> v2 (2026-08-27)：新增 30 秒规则、不记清单、解法动态真相源（AI/智能体范围；工作域待确认）、lane 规则。

## 一、原则

1. **无例外投递**：四工具谁遇到问题/完成修复，谁（或其操作人）负责投递。不允许「记在脑子里」「下次再说」。
2. **先查库再建卡**：投递前 `kedb.py check`；命中 = 复发，走 repeat_count 流程，不重复建卡。
3. **裁判独立**：卡片的 recorded_by 是投递工具身份（hermes-A/codex-A/dsh-A/gpt-A/huohaochen），evaluator 必须是「第二裁判」或人。工具不能既记录又评估。
4. **AI 自报降权**：工具的「自报」只是捕获信号，不是结论。severity 定级与 KEDB 登记由人最终确认（GPT 通道尤其如此）。
5. **只存系统问题**：本库只收工具故障/误判/越权/配置坑；内容判断类问题归主账号（Notion / 内容判断引擎）。

## 二、投递阈值（什么必须投）

- **真实故障**：报错、崩溃、API 异常、数据损坏、配置错误。
- **误判**：把错误结论当事实输出、把空返回当数据为空、被注入误导。
- **越权/失控**：未经授权改文件、自我适配验收标准、突破工具边界。
- **坑**：绕了半小时以上的问题，即使最终解决了。

**不需要投**：一次性小笔误（当场改掉且不可复现）、纯内容问题。

## 三、各工具通道

| 工具 | 通道 | 命令 |
|------|------|------|
| DSH | 直接建卡 | `python3 ~/Desktop/系统问题反馈引擎/scripts/new_card.py problem "标题" --tool dsh` |
| Codex | 直接建卡 | 同上，`--tool codex` |
| Hermes | 直接建卡 | 同上，`--tool hermes`（SOUL.md 已内置） |
| GPT/ChatGPT | 人肉投递 | 把 GPT 的结论复制成 `00-Inbox/` 快速投递（`source_tool: gpt`），由人跑 `ingest.py` |

- 修复方案：`new_card.py change "标题" --tool <工具>`；沉淀原则：`new_card.py calibration "标题" --tool <工具>`。
- 修复完成必须回填：P 卡 status/process_captured；C 卡 verdict/calibrated 走既有门控（judgment_change 必带 calibration_ref）。

## 四、字段约定（V3.2）

| 字段 | 取值 | 说明 |
|------|------|------|
| source_tool | hermes / codex / dsh / gpt / human / other | 谁投递，默认 human |
| recorded_by | hermes-A / codex-A / dsh-A / gpt-A / huohaochen | 投递身份，与 source_tool 映射 |
| ke_ref | KE-xxx | KEDB 命中时回指，复发必填 |
| severity | S1 / S2 / S3 / S4 | S1 致命一次即升，S4 轻微批量处理 |
| detected_at | ISO datetime | 问题实际发生时间（算 MTTD） |

## 五、KEDB 与复发

- 先查：`python3 scripts/kedb.py check "症状"`。
- 复发：`ingest.py` 自动 repeat_count+1 并挂 ke_ref；手工建卡则填 ke_ref。
- 新问题不自动入 KEDB；人工确认是「已知顽疾」后手工登记 known_error_db.json。
- 命中 S1 条目 → 风险矩阵一次即升。

## 六、防自报条款

- GPT 通道必须人确认后才入库：`source_tool: gpt` 表示「GPT 的结论，人已背书」。
- 工具不得自行修改 schema.json / known_error_db.json / 本协议（规则变更走 13_rule_candidates 方向阀 + 人工确认）。
- 工具不得把「自报的问题」直接判 severity=S1（S1 由人定）。
- 工具的「已解决」声明不算数：以 validate_loop.py 门控 + 人复评为准。


## 七、30 秒规则

能 30 秒写清「症状 + 触发条件 + 怎么解决」的问题才建卡；写不清=未成熟，先丢 00-Inbox 或口述给工具整理。

## 八、不记清单（负清单）

- 一次性笔误（当场改掉且不可复现）不记
- 纯情绪、吐槽不记
- 无验证信号的工作直觉只进灵感层，不建 P 卡
- 工具自报 severity=S1 无效（S1 只能人定）

## 九、解法动态真相源（当前范围：AI/智能体使用问题）

- 每张已解决 P 卡的 solution 带 solution_level（待验证/已验证/被推翻）与 solution_hits（事实验证有效次数）
- 人用 `python3 scripts/ticket.py verify <ID> 有效|无效` 确认：有效→已验证+hits+1；无效→被推翻
- 被推翻的解法在 kedb.py check 输出中显著标注，禁止再当有效方案推荐
- 铁律：解法永远只是实战经验（动态真相源），永远变不成第一真相源；第一真相源=课程方法论（IP运营第二大脑）
- 短视频运营（工作域）持保留意见，待确认状态

## 十、lane 规则（三个仓库分工，互不越界）

- 发生的问题 + 怎么修 → 本引擎（SIFE）ticket.py 建卡
- 做的判断 + 等数据验证 → 内容判断校准引擎（VideoLoop）
- 学到的方法 + 课程方法论 → IP运营第二大脑
